# API sources and boundaries

This is an unofficial integration. It follows ordinary Maccabi portal behavior, published service pages, and official frontend code. Maccabi does not promise these internal web interfaces will stay compatible. Unsupported response shapes are rejected instead of guessed.

The imaging-viewer chain and its four read endpoints live in [readers/imaging-viewer.ts](https://github.com/orenyomtov/maccabi-health/blob/main/packages/core/src/readers/imaging-viewer.ts). The viewer's own host is on the transport's origin allowlist only because of that chain, and the one portal request whose success is a redirect to the login host (which is otherwise this client's expiry signal) carries a single-destination opt-out rather than a relaxation of the shared rule.

Account methods live in [the shared readers](https://github.com/orenyomtov/maccabi-health/blob/main/packages/core/src/readers/index.ts), with separate [legacy HTML](https://github.com/orenyomtov/maccabi-health/blob/main/packages/core/src/readers/legacy.ts) and [quarterly billing](https://github.com/orenyomtov/maccabi-health/blob/main/packages/core/src/readers/billing.ts) parsers. The links above describe service purpose. Exact requests and accepted fields are defined in code and checked with synthetic tests. Public documentation alone does not establish every endpoint or response schema.

## Contract handling

Account requests use the owner from the verified login bootstrap. Dependent selection and caller-supplied account switching are excluded.

Document downloads resolve fresh owner-list or detail references. Private routing values and signatures stay internal. Fixed destination, query, MIME, and PDF-byte checks protect that boundary. Core PDF methods cap documents at 2 MiB, enforced while the body is read rather than after it.

Legacy HTML accepts only the supported encodings and page structures. Hidden controls and account banners are excluded from returned content.

The public directory reads category-specific field/city catalogs for doctors and labs/institutes/therapists. Search supports one field, optional city/provider name and a bounded page. Detail re-runs the same returned search context and resolves a provider reference against fresh results. It sends no account cookies or `Authorization`. Browser search/page/detail responses were observed, but library live search remains unverified: the host answers this client with a bot-challenge page, on the doctors entry page and on the JSON endpoints alike. Nothing is retried or bypassed. Use the official directory in a browser when the expected response is unavailable.
