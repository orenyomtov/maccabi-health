# Capabilities and limits

The library, CLI, and MCP expose the same operations. This is a supported slice of Maccabi, not portal parity.

Contracts were taken from ordinary portal traffic or complete official frontend source, then checked with synthetic tests. Some methods also have live client checks; others are source-backed and tested offline. Inquiry approval PDFs remain live-unexercised. Visit-summary, inquiry-associated referral, and quarterly report PDFs have matched browser downloads, with those getters tested offline.

Original clinical text, units, dates, and PDF bytes may identify the patient. The CLI and MCP omit private routing and signature fields from structured output; core methods return the source record as it arrived, so a library caller who wants the same output applies the exported `safeClinical` filter themselves. Filtered or not, that is not anonymized or de-identified. These operations do not diagnose and do not claim a complete history.

The MCP column names the call, which is not always its own tool. Every row an MCP list tool returns carries an opaque `ref`; `maccabi_detail` reads the record behind one and `maccabi_document` returns its original PDF, so most per-row operations are a ref passed to one of those two rather than a tool of their own. `maccabi_report` covers the account-wide PDFs that belong to no row, and `maccabi_account` covers the member's own account record - identity, contact fields, authorized viewers, notification registration and payment authorization - one `section` at a time. The library and the CLI still take the raw identifiers, and those identifiers are still in every MCP row. The ref exists so a caller cannot pair one row's request id with another row's document id, which is a mistake the raw form allows and the ownership check only catches afterwards. `maccabi_capabilities` returns this same map at runtime, along with worked journeys through it.

### The public directory is behind a bot challenge

`serguide.maccabi4u.co.il` sits behind a bot filter that scores the client rather than applying a fixed rule. All four public-directory operations are affected: a call may succeed once and then fail on the next identical request seconds later. Two symptoms, one cause - the challenge page is HTML, so the doctors path reaches it, finds no embedded search configuration and reports `DIRECTORY_CONFIGURATION_UNAVAILABLE`, while the labs path asks for JSON, gets HTML and reports `DIRECTORY_INVALID_RESPONSE`. The endpoints did not move and nothing about the account session is involved; these reads never used one.

This client sends an honest `User-Agent` naming itself, its version and its issue tracker. It does not impersonate a browser, replay challenge cookies or retry to wear the filter down, which means the challenge is not something it can reliably get past. Everything else in this table is unaffected - the directory is a separate public host from the member portal.

## Imaging studies: what is verified and what is not

An `imaging_study` test row carries no attached document, so `imaging-pdf` correctly refuses it. The portal shows those scans by handing the member off to a separate viewer, MedDream by Softneta, on Maccabi's own `meddreamy.maccabi4u.co.il`, behind an F5 BIG-IP APM. This client walks that handoff itself: eight ordinary HTTP hops, two of which are auto-submitting HTML forms whose hidden inputs it reads out of the markup. No browser, no JavaScript, no bearer token.

**The whole chain has been executed against the live viewer**, twice, on 2026-09-23. All five commands exit 0. What was measured: the study's structure and all 11 per-instance metadata reads; a 6,631-byte baseline JPEG thumbnail with the right magic number and trailer; pixel buffers whose length matched `rows x columns x samplesPerPixel x (bitsAllocated / 8) x numberOfFrames` exactly on every one of the 11 instances, including an RGB instance at `samplesPerPixel: 3` and 4,516,320 bytes, which is what confirms the arithmetic for 3-sample data rather than only for the 1-sample case where two factors are 1. The Secondary Capture instance, previously listed here as untested because the portal's own viewer skips it, is served on request. No hop returned `AUTH_REQUIRED`, and the portal session was still `verified: true` afterwards. The ownership check was negative-tested live at all three UID levels: mutating the study, series or image UID alone each returns `OWNER_MISMATCH` with nothing written. Full run notes are in [Live validation](https://github.com/orenyomtov/maccabi-health/blob/main/docs/research/LIVE-VALIDATION.md).

What remains unverified:

- **Only 8-bit ultrasound is evidenced**, single-frame, in both 1-sample and 3-sample form. CT and MR are 16-bit and may be multi-frame, and no such study has been read. The buffer length is computed generically from the metadata and checked against the bytes actually returned, so a wrong assumption fails loudly rather than silently producing a garbled image.
- **No error response has ever been captured**, not in the capture, and not in the live runs, which produced no errors to observe. Nothing is known about what the viewer returns for an expired session, a wrong storage id, or a study UID the session was not handed. Failures are mapped onto the ordinary read-error codes on the assumption that the status code means what status codes usually mean. That assumption is untested.
- **Token and URL lifetimes are unmeasured.** How long the handoff URL stays valid, and whether the viewer token is single-use, are both unknown. A viewer session is therefore established per study and re-established for each new reader.
- **Whether the viewer binds its own session to the studies it handed out is still unknown.** The live runs only ever asked for the owner's own study, which the viewer served; that says nothing about what it would do with someone else's. Because there is no evidence either way, this client does the constraining: the study UID must be the `request_id` of an `imaging_study` row on a freshly fetched owner list, and the series and image UIDs must appear in that study's own structure. Note one asymmetry: the document downloads bind the `(request_id, doc_id)` pair, while the viewer URL takes `request_id` alone, so this is a single-field check.
- **The handoff URL is itself a credential.** It embeds the member id, its code and the member's `checksum_id`, which is per-member rather than per-study and authorizes every study the member has. It is built inside the library, used once, and never returned, printed or logged.
- **Viewer payloads are dense PHI.** The study tree names the patient at its top level and gives their birth date; per-image metadata adds the accession number, the rendered corner labels and a bag of raw DICOM tags holding the patient name, birth date, referring physician and institution under hex keys. It goes through the same omit filter as every other read, on the same terms, and that filter drops the bag rather than picking through it. The filter drops identifiers, not clinical facts, so patient sex survives it.
- **PHI leaves this project's boundary at the handoff.** Everything past it is a third party's application handling the member's imaging.

Image bytes are available from the CLI only. `imaging-thumbnail` writes a JPEG; `imaging-pixels` writes the raw buffer and prints the geometry without which the file cannot be read at all. No MCP tool returns image bytes: a megabyte-scale binary is useless in a model's context and expensive to put there.

## Authentication and output

CLI login uses masked ID/SMS prompts, or the `--id` and `--code` flags where there is no terminal, and saves the session to an owner-only file in the config directory. Those flags and the `MACCABI_ID`/`MACCABI_OTP` variables put the ID number and the code in argv and the environment. An unfinished challenge is a second owner-only file that expires after ten minutes. SMS is never retried automatically, and a rejected code ends the challenge instead of allowing another attempt. See the [CLI guide](CLI.md).

Both MCP transports resolve the credential lazily, on the first account tool call, but not from the same place. Stdio reads the CLI's `session.json`, so a terminal login signs it in. Loopback Streamable HTTP requires OAuth 2.1, signs the member in through their own browser, and keeps one credential file per member under `sessions/`; a CLI login does not carry into it. Starting either transport does not log in or touch any saved credential. Public directory tools do not use an account session. Missing or expired account sessions return login guidance, never SMS or auto-login. `maccabi_login_start` and `maccabi_login_verify` drive the sign-in from a client over stdio, with the ID and code entering the model's context; over HTTP they are not registered, because the browser leg replaces them. `maccabi_login_status` and `maccabi_logout` exist on both.

`renew-session` / `maccabi_renew_session` send one ordinary renewal request. CLI `keep-alive` repeats only for an explicit finite duration. Neither guarantees continued authentication or resets a browser idle timer. Keep-alive's effect, measured live on 2026-09-23, is the difference between the two server clocks: it holds off the idle timeout, and it cannot move the 3600-second absolute cap that starts at login. Expect to log in again every hour regardless. Session maintenance is not prescription renewal. Forced reauthentication needs a fresh login: interactive, or the `--id`/`--code` flags and their tool equivalents.

CLI PDFs are new files, mode 0600, no overwrite. Core PDF methods cap documents at 2 MiB, so the CLI does not bypass the document bound. MCP JSON is capped at 128 KiB and original PDFs at 2 MiB. Only commands and tools that advertise local `--limit` / `--offset` (CLI, max 1000) or list paging (MCP, default 20, max 50) accept them. They slice a newly fetched response and do not load further upstream pages. Clinical history, retention, and upstream pagination are incomplete.

## Unsupported

Out of scope: booking, changing, or cancelling appointments; prescription renewal; message or request submission; payment; profile updates; delegation; dependent access; mark-read. Availability stops after the documented clinic-mode conversation.

Read gaps still unsupported: additional clinical-history/server pages, further inquiry or document subtypes, arbitrary custom-selected laboratory printing, populated monthly billing itemization/receipts, DICOM P10 export or reports from the imaging viewer, and separate dental, complementary-medicine, or app-only systems. Public directory treatment/multi-field filters, complete price/team/service relationships and categories beyond doctors/labs-and-therapists remain unavailable. These gaps are distinct from the excluded writes above; the existing command inventory does not establish full portal coverage.

Conditional and separate-context records are also outside the implemented slice: mental-health treatment history, child-development assessments, the special soldier/prisoner/former-member record view, and app questionnaires or measurements. The observed current-owner menu does not establish those contracts. General mailings support the three known display branches and eligible PDFs; complete archive retention remains unverified. Visible webpage/video links are returned without fetching them.
